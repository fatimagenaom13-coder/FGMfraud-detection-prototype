# AI-Based Fraud Detection and Transaction Security Module — Prototype

**Author:** Fatima Altagracia Genao Mendez
**Status:** Proof-of-concept prototype, Phase 1 (early development)
**Purpose:** Initial technical demonstration of the proposed endeavor described in the
petitioner's I-140 / National Interest Waiver petition (Model or Business Plan, Prong I).

## What this is

This repository contains an early-stage, working prototype of the three core technical
components described in the petitioner's proposed endeavor: an AI-based fraud detection
and transaction security module designed to be integrated into the systems of community
banks and credit unions in the United States.

The goal of this prototype is not to be a finished product. It is evidence of concrete,
dated technical progress toward the endeavor described in the petition — a first working
implementation of the detection logic that the Model or Business Plan describes at a
conceptual level, built and tested by the petitioner herself.

## Important note on the data

All data used in this prototype (`data_accounts.csv`, `data_transactions.csv`) is
**100% synthetic**, generated by `generate_synthetic_data.py`. It does not contain,
represent, or derive from any real customer, account, or transaction data from
Banreservas, Fiserv, or any other financial institution. Synthetic data is standard
practice for prototype and research-stage fraud-detection work, precisely because real
transaction data is confidential and cannot be used outside a production environment
governed by a bank's own data-security controls. The synthetic dataset is designed to
reproduce the general statistical shape of real transaction activity (typical purchase
amounts, account activity levels, time-of-day patterns) and to include intentionally
injected examples of two fraud patterns, so that the detection logic has something
realistic to find.

## The three components

### 1. Supervised classification (`run_supervised_classifier`)
A Random Forest classifier trained on labeled transaction data to recognize known fraud
patterns (e.g., unusually large transactions at unusual hours through card-not-present
channels). This corresponds to the "known pattern" layer of the module described in the
Business Plan — the layer that catches fraud typologies the system has already learned to
recognize.

### 2. Unsupervised anomaly detection (`run_anomaly_detection`)
An Isolation Forest model that flags transactions that look statistically unusual, without
relying on any fraud label. This corresponds to the module's second layer, intended to
catch novel fraud patterns that have not been seen before and therefore could not have been
included in a labeled training set — an important complement to the supervised layer, since
fraud tactics change constantly.

### 3. Network / graph analysis (`run_graph_analysis`)
A graph-based analysis of the flow of funds between accounts, using account-to-account
transfer data to detect small, densely-interconnected clusters of accounts — a pattern
consistent with "layering" or "structuring," a common money-laundering technique in which
funds are passed rapidly between multiple accounts to obscure their origin. This corresponds
to the module's anti-money-laundering (AML) review layer described in the Business Plan.

## How to run it

```bash
pip install pandas numpy scikit-learn networkx
python generate_synthetic_data.py     # creates data_accounts.csv and data_transactions.csv
python fraud_detection_prototype.py   # runs all three components and prints results
```

Sample output from an actual run is saved in `run_output.txt`.

## Relationship to the Model or Business Plan

This prototype corresponds to the work planned for **Phase 1 (Months 1–8): Core Module
Development** in the Business Plan submitted with the petition. It demonstrates that the
three analytical approaches described there — supervised classification, unsupervised
anomaly detection, and graph-based network analysis — are technically viable and that the
petitioner has already begun building them, rather than these being purely conceptual or
aspirational. Later phases described in the Business Plan (pilot integration with a real
institution under a data-security agreement, regulatory compliance alignment, and
multi-institution licensing) are the next steps beyond this prototype and are not addressed
by this code.
